## 2. Task 1.1 — Create MealMemberServing Model

**Action:** Create a new file.
**File path:** `backend/models/meal_member_serving.py`

### Purpose

`MealMemberServing` is the central new table of this redesign. It stores, for every meal in a joint profile plan, the individual serving information for each household member: their portion description, human-readable adjustment text, and their per-serving nutritional breakdown.

### Schema Design Rationale

- **`member_name` is denormalized** (stored directly, not looked up via FK at read time) so that if a profile is later deleted, historical plan data still displays correctly.
- **`adjustment`** is a short, human-readable string like `"half rice, extra dal, skip garnish"`. It is generated by the LLM in Workflow A's Step 4 (see Overview spec) or directly by the LLM in Workflow B.
- **`portion_description`** is more detailed, optionally including gram weights (e.g., `"150g rice, 200g dal, full salad bowl"`). This is for the recipe detail view.
- **Nutrition fields (`calories`, `protein`, `carbs`, `fats`, `fiber`)** are this member's share of the meal, not the total meal nutrition. The sum of all members' `calories` for a given `meal_id` should approximately equal the base `Meal.calories` (it won't be exact because different members get different portions).
- **`UniqueConstraint("meal_id", "member_profile_id")`** ensures there is exactly one serving record per member per meal. If re-generation creates new servings, the old ones must be deleted first (or the router upserts them — the router spec in Phase 4 covers this).

### Complete Model Definition

```python
# backend/models/meal_member_serving.py

"""
MealMemberServing model — stores per-member portion data for joint profile meals.

This table is only populated for meals belonging to joint profile WeeklyPlans.
For solo profile plans, this table has no rows for those meals.

Schema design notes:
  - member_name is denormalized for resilient historical display.
  - adjustment is LLM-generated human-readable text (e.g., "half rice, extra salad").
  - portion_description optionally includes gram weights for recipe detail view.
  - calories/protein/carbs/fats are this member's share (not the full meal total).
  - UniqueConstraint prevents duplicate serving records per (meal, member) pair.
"""

from sqlalchemy import Column, Integer, Float, String, Text, ForeignKey, UniqueConstraint
from sqlalchemy.orm import relationship
from database import Base


class MealMemberServing(Base):
    """
    Per-member serving allocation for a single meal in a joint profile plan.

    Relationships:
      meal         — parent Meal (many-to-one); backref adds meal.member_servings list
      member_profile — the household member's UserProfile (many-to-one, no backref)
    """

    __tablename__ = "meal_member_servings"

    # ---------------------------------------------------------------------------
    # Primary Key
    # ---------------------------------------------------------------------------
    id = Column(
        Integer,
        primary_key=True,
        autoincrement=True,
    )

    # ---------------------------------------------------------------------------
    # Foreign Keys
    # ---------------------------------------------------------------------------
    meal_id = Column(
        Integer,
        ForeignKey("meals.id", ondelete="CASCADE"),
        nullable=False,
        comment="Parent meal this serving belongs to. CASCADE ensures cleanup on meal delete.",
    )
    member_profile_id = Column(
        Integer,
        ForeignKey("user_profiles.id", ondelete="CASCADE"),
        nullable=False,
        comment="The individual household member's UserProfile id.",
    )

    # ---------------------------------------------------------------------------
    # Display Fields
    # ---------------------------------------------------------------------------
    member_name = Column(
        String(100),
        nullable=False,
        comment="Denormalized member name for display; resilient to profile deletion.",
    )

    # ---------------------------------------------------------------------------
    # LLM-Generated Adjustment Text
    # ---------------------------------------------------------------------------
    adjustment = Column(
        Text,
        nullable=True,
        comment=(
            "Human-readable portion adjustment. "
            "Generated by LLM. "
            "Examples: 'half rice, extra salad, add cucumber raita', "
            "'no garnish peanuts, full portion', 'skip rice, double dal'."
        ),
    )
    portion_description = Column(
        Text,
        nullable=True,
        comment=(
            "Detailed portion description with gram weights where available. "
            "Example: '150g basmati rice, 200g dal tadka, 1 full salad bowl (120g)'."
        ),
    )

    # ---------------------------------------------------------------------------
    # Per-Member Nutritional Data
    # ---------------------------------------------------------------------------
    # These values reflect THIS member's share of the meal, not the total meal.
    # In Workflow A (LP), these are computed from LP allocation fractions * component nutrition.
    # In Workflow B (LLM-only), these are generated directly by the LLM.
    calories = Column(
        Float,
        nullable=False,
        comment="This member's calorie share for this meal.",
    )
    protein = Column(
        Float,
        nullable=False,
        comment="This member's protein share in grams.",
    )
    carbs = Column(
        Float,
        nullable=False,
        comment="This member's carbohydrate share in grams.",
    )
    fats = Column(
        Float,
        nullable=False,
        comment="This member's fat share in grams.",
    )
    fiber = Column(
        Float,
        nullable=True,
        default=0,
        comment="This member's fiber share in grams. Nullable for backward compat.",
    )

    # ---------------------------------------------------------------------------
    # Constraints
    # ---------------------------------------------------------------------------
    __table_args__ = (
        UniqueConstraint(
            "meal_id",
            "member_profile_id",
            name="uq_meal_member_serving",
            # One serving record per (meal, member) pair.
            # The meal plan generation router must DELETE existing rows before
            # inserting new ones when regenerating (not upsert) to avoid
            # constraint violations. See Phase 4 (routers/meal_plan.py) spec.
        ),
    )

    # ---------------------------------------------------------------------------
    # Relationships
    # ---------------------------------------------------------------------------
    # NOTE: backref="member_servings" automatically adds a `member_servings`
    # attribute to the Meal class. However, Task 1.3 below replaces this backref
    # with an explicit relationship on the Meal side (using back_populates) for
    # clarity and to enable cascade="all, delete-orphan" on the Meal side.
    # When Task 1.3 is done, change this to: back_populates="member_servings"
    meal = relationship(
        "Meal",
        back_populates="member_servings",
    )
    member_profile = relationship(
        "UserProfile",
        # No backref — UserProfile does not need a reverse list of servings.
        # Foreign key must be specified explicitly because UserProfile has
        # multiple FK paths from this table (meal_id and member_profile_id
        # both eventually reach user_profiles via different routes).
        foreign_keys=[member_profile_id],
    )
```

### Column Summary Table

| Column | SQLAlchemy Type | Nullable | Default | Purpose |
|---|---|---|---|---|
| `id` | `Integer` | No | autoincrement | PK |
| `meal_id` | `Integer` (FK → meals.id) | No | — | Parent meal |
| `member_profile_id` | `Integer` (FK → user_profiles.id) | No | — | Household member |
| `member_name` | `String(100)` | No | — | Denormalized display name |
| `adjustment` | `Text` | Yes | `None` | Human-readable serving note |
| `portion_description` | `Text` | Yes | `None` | Detailed portion with gram weights |
| `calories` | `Float` | No | — | Member's calorie share |
| `protein` | `Float` | No | — | Member's protein share (g) |
| `carbs` | `Float` | No | — | Member's carb share (g) |
| `fats` | `Float` | No | — | Member's fat share (g) |
| `fiber` | `Float` | Yes | `0` | Member's fiber share (g) |

### Unique Constraint

```
uq_meal_member_serving: UNIQUE (meal_id, member_profile_id)
```

This is enforced at the database level. If a code path tries to insert two serving records for the same member in the same meal, SQLite will raise `sqlite3.IntegrityError: UNIQUE constraint failed`. The generation router must handle this by deleting existing `MealMemberServing` rows before inserting new ones.

### Decision: Explicit Relationship with `back_populates`

We use `back_populates="member_servings"` (not `backref`) so both sides of the relationship are explicitly declared. This is the SQLAlchemy 2.x recommended pattern and makes the relationship immediately visible when reading `meal_plan.py` without having to look up `meal_member_serving.py`.

The `cascade="all, delete-orphan"` on the `Meal` side ensures that when a `Meal` row is deleted (e.g., via `db.delete(meal)`), all its `MealMemberServing` rows are automatically deleted by SQLAlchemy before the `DELETE FROM meals` statement. This is in addition to the `ondelete="CASCADE"` on the FK, which handles raw SQL deletes.

**Important:** Because we use `back_populates` on both sides, the `MealMemberServing.meal` relationship (defined in Task 1.1) must use `back_populates="member_servings"`, NOT `backref="member_servings"`. Task 1.1 already shows this correctly.

## 5. Task 1.4 — Remove is_primary from JointProfileMember ORM

**Action:** Modify an existing file.
**File path:** `backend/models/joint_profile.py`

### Rationale

`is_primary` was used to determine which member's qualitative preferences (diet_type, allergies, etc.) would be copied to the joint profile. Under the new system, preferences are merged algorithmically (union of allergies, strictest diet type, etc.) — the concept of a "primary" member no longer applies to preference inheritance.

**The column is NOT dropped from the database.** SQLAlchemy does not enforce schema parity: if a column exists in the DB but not in the ORM model, SQLAlchemy simply ignores it. This means:
- Existing rows with `is_primary=1` or `is_primary=0` are unaffected.
- No data loss.
- No migration needed for this specific change.
- Old code that set `is_primary` still worked; it just set a column that is now invisible to the ORM.

### Before (current file — full content):

```python

        nullable=False,

    member_profile_id = Column(
```

### `server_default` vs `default`

- `default=WORKFLOW_DEFAULT` — applied by SQLAlchemy in Python before the INSERT. New `User` objects created via ORM get this value automatically without explicitly setting it.
- `server_default=WORKFLOW_DEFAULT` — written to the `DEFAULT` clause of the `CREATE TABLE` or `ALTER TABLE` statement. This ensures that any rows added via raw SQL (e.g., test fixtures, seed scripts) also get the correct default.

Both must be set to ensure consistent behavior across ORM and raw SQL access patterns.

## 7. Database Migration

SQLite used in this project does not support all DDL operations, but it does support `ALTER TABLE ... ADD COLUMN`. The `MealMemberServing` table is new (auto-created via `Base.metadata.create_all()`). The `family_meal_workflow` column is new on an existing table and requires a migration.

### Option A: Drop and Recreate (Development Only)

**Use only in local development. Never in production or staging with real user data.**

```bash
# From the project root
rm health_advisor.db
# Then restart the backend — create_all() recreates all tables from scratch
cd backend && ./venv/bin/python -m uvicorn main:app --reload --port 8000
```

This is the simplest path during development when no real data needs to be preserved.

### Option B: Manual ALTER TABLE Migration (Recommended for Staging/Production)

Run this SQL against the existing database before restarting the backend.

```sql
-- Migration: Add family_meal_workflow to users table
-- Run with: sqlite3 health_advisor.db < migration_phase1.sql
-- Or interactively: sqlite3 health_advisor.db

-- Step 1: Add the new column with a default value
-- SQLite's ALTER TABLE only supports ADD COLUMN, not MODIFY or DROP.
-- The DEFAULT clause sets the value for all existing rows.
ALTER TABLE users
ADD COLUMN family_meal_workflow VARCHAR(20) NOT NULL DEFAULT 'hybrid';

-- Step 2: Verify the column was added
PRAGMA table_info(users);
-- Expected output includes a row:
-- cid | name                  | type        | notnull | dflt_value | pk
--  7  | family_meal_workflow  | VARCHAR(20) |    1    | 'hybrid'   |  0

-- Step 3: Verify existing rows got the default
SELECT id, email, family_meal_workflow FROM users LIMIT 5;
-- All rows should show 'hybrid'
```

Save this as a file for team use:

**File path:** `backend/migrations/phase1_add_family_meal_workflow.sql`

```sql

-- Applied: 2026-02-22
-- Ticket: Joint Profile Redesign — Phase 1

```

### MealMemberServing Table Creation

The `meal_member_servings` table does **not** need a manual migration. It is a brand-new table. When the backend starts up and calls `Base.metadata.create_all(bind=engine)` (in `backend/database.py` or `backend/main.py`), SQLAlchemy creates any tables that don't yet exist. Since `meal_member_servings` does not exist before this phase, it will be created automatically on the next startup after `MealMemberServing` is imported in `models/__init__.py`.

**Verify table creation:**

```bash

# Should include: meal_member_servings

# Check the schema

```

Expected schema output:

```sql
CREATE TABLE meal_member_servings (

    meal_id INTEGER NOT NULL,
    member_profile_id INTEGER NOT NULL,
    member_name VARCHAR(100) NOT NULL,
    adjustment TEXT,

    calories FLOAT NOT NULL,
    protein FLOAT NOT NULL,

    fiber FLOAT DEFAULT '0',

    CONSTRAINT pk_meal_member_servings PRIMARY KEY (id),
```
